# Исследования: память сессии без LLM-суммаризации

Заметка-изыскание (дискуссия 2026-10-07) + план доработки. Тема: заменить big-bang
LLM-суммаризацию при переполнении контекста на механическую память с индексами, и где
именно LLM всё-таки нужна. Связано с [[context_management]], [[session_resume]],
entities/tools/session-memory.md.

## 1. Исходное состояние (проверено по коду)

- Тримм перед запросом: `core/textual_integration.py:110` (`_prepare_messages_for_ollama`) —
  оценка токенов `len//4` (:86), budget = `num_ctx − 1200`, выбрасываемое в артефакт
  `context_trim_*.json`. Режет сообщения по одному, может осиротить `tool`-ответ от
  `assistant.tool_calls`.
- Жёсткий триггер: `prompt_eval_count + eval_count ≥ 0.90·num_ctx` (:1312, `HARD_CTX_PCT`);
  дополнительные триггеры — детекция зацикливания (:155) и `MAX_TOOL_ROUNDS_PER_TURN=80`.
- Суммаризация: `_ollama_summarize_and_reset_context` (:303) — вся история в артефакт,
  один вызов (`num_predict=450`) рождает прозу `SESSION_PROTOCOL`
  (prompts/context_overflow_*.txt), история очищается до system + протокол.
  Бюджет восстановлений `MAX_AUTO_RECOVERIES_PER_TURN=2`.
- Stealth/pipe (`botinok.py:453,548`) умеет только тримм, без суммаризации.
- `session_memory` (`tools/session_memory.py`): объектная модель Turn/ToolCall, 9 действий,
  EXACT/DERIVED/HINT, прощающий синтаксис; поиск — линейный перебор + построчный обход
  файлов сессии (`файл:строка + timestamp`). word-индекс `.index/session_memory.idx`
  декоративный: индексирует только `[a-zA-Z_]`, кириллица не попадает; поиском не используется.

## 2. Оценка внешнего whitepaper (идейно)

Идея «Context RAM / Event Log» верна, ~60% уже есть в botinok (артефакты, лог, поисковый
инструмент, auto_continue). Ценное: инкрементальная дистилляция вместо big-bang;
градуированный pressure-инжект в tool-result; дошивка при `finish_reason=length`.
Слабое: фиксированное «последние N сообщений» хуже токен-бюджета; «точный замер до
запроса» иллюзорен (Ollama отдаёт метрики только после ответа); асинхронный LLM-вызов на
каждый шаг на одной GPU конфликтует с основным инференсом; критика «испорченного телефона»
самоприменима к их микро-суммаризациям; «модель инстинктивно сократит рассуждения» — спекуляция.

## 3. Принципы решения: бюджетный харнес с механической памятью

1. Не плодить LLM-вызовы на одной GPU; детерминизм везде, где возможен.
2. Память = библиотека, не пересказ: полный лог immutability + указатель; в контексте —
   только каталог забытого.
3. Метрика качества индекса — recall@k (нашёл ли агент нужное), а не читабельность.
4. Каждое вытеснение обратимо через существующий лог и `session_memory`.
5. LLM платит вниманием только за то, что нельзя знать детерминированно.

## 4. Эксперимент: дайджест реальных сессий без LLM

Материал: две крупнейшие sample-сессии (одна — диалоговая, ~12 юзер-шагов; другая — одна
пользовательская задача, выполненная 16 автономными вызовами модели). Инструменты: stdlib +
`pymorphy3` (лемматизация, не LLM; установлен в venv). Прототипы: `/tmp/kilo/digest*.py`.

Результаты:
- Полная лента итераций строится за миллисекунды из `tools.log` + `steps/` + `context.json`;
  сюжет сессии восстанавливается без единого LLM-вызова, включая развязку (ключевые сущности
  видны прямо в аргументах инструментов).
- **Правильная гранулярность окна — вызов модели, а не юзер-реплика**: границы —
  `metrics`-события `session_raw.log` (их число = число вызовов), инструменты привязываются
  по таймстампам. Иначе автономная цепочка из 16 вызовов слипается в один «ход».
- **Облако терминов на окно** (~10 лемм + подписи инструментов, отсев сквозных слов):
  читается как микро-чейнжлог; пустое облако = честный сигнал «ход без прогресса»
  (детектор зацикливания: сходство соседних облаков ≈ 1); в рабочих сессиях терминалы —
  пути/идентификаторы/команды — ровно то, что LLM-суммаризаторы портят.
- Повторы-ретраи видны как серии одинаковых окон с почти равным ctx.

Найденные проблемы данных (чинить при случае): `context.json` дублирует user-реплики ×3–4
(партер session_memory дубли уже отсекает при чтении); `steps/step_*.json` пишется не на
всех путях; word-индекс ASCII-only.

## 5. Облако терминов и методика LLM-wiki

Облако тегов исторически (folksonomy) было навигационным слоем и умерло от синонимов,
частотности и спама. Методика LLM-wiki решает то же самое: контролируемый словарь (схема
тегов AGENTS.md), canonical entity pages, index-first workflow, грепаемый log. Вывод:
индекс не обязан быть понятным — он обязан давать recall; для этого механических токенов
достаточно, проза индексу не помогает.

## 6. Где LLM нужна и где не нужна

- Микро-LLM, жующая сырой лог по одному ходу: дорого (GPU-конфликт), теряет точные сущности,
  тормозит основную работу — отвергнуто.
- Микро-LLM **над механическим остовом** (вход — готовые строки skeleton'а, выход —
  проверка множеством: каждая сущность ответа обязана присутствовать во входе): оправдана,
  один вызов на вытеснение пачкой, не на ход.
- **Основное решение — принудительная подпись шага самой моделью** (харнес подписаний):
  внутренняя `sign_step`, форсированный вызов один раз на ход (OpenAI-бэкенд:
  `tool_choice=required`; нативный Ollama: директива + retry-паттерн `auto_continue_final`).
  Жёсткие правила: схема без свободной прозы (`goal/done ≤15 слов`, `status` enum),
  `entities` — только закрытый список того, что харнес реально видел в ходе; верификация
  подстрокой по skeleton'у; в чат и в messages не попадает. Нет подписи — механическая
  строка, деградация без поломки. Подписчик сидит внутри контекста шага — источник
  галлюцинаций исчезает, VRAM не тратится.

## 7. Целевая архитектура

Блок **«скользящее окно о забытом»** — одна system-реплика, регенерируемая на каждый
запрос (не записи в истории — иначе сама вытеснится), взамен нынешней notice про артефакт:

```
## [HH:MM:SS] wNN ☁ <≤10 лемм окна>   goal: … | done: …   (из sign_step, если есть)
   sm get_turn turn_id=… | tools: <подписи> | ctx=<число>
```

- строка = механический skeleton окна + (при наличии) goal/done из подписи модели;
- указатели — языком `session_memory` (`get_turn turn_id=…`, `файл:строка`);
- бюджет: 15–20 токенов на окно, кап блока 400–600 токенов; древние окна иерархически
  мёржатся (10 строк → 1 частотным переизбранием терминов, без LLM);
- вытеснение по границам ходов ⇒ инвариант «вытеснено сообщение ⇒ закрыто окно».

## 8. Регресс 2026-10-10: шторм ресетов в обход плавающего контекста

Сессия `20261010_202930_visual_run`: 13 overflow-ресетов каскадом за 15 минут,
0 `context_trim_*`, FORGOTTEN_INDEX не построился ни разу. Причины:

1. `_append_turn_guidance` вызывался на каждом tool-раунде (не на ходе) и
   дописывал копию system-памятки TOOL_USAGE_REMINDER; system-реплики
   неприкосновенны и для тримма, и для ресета → 325 копий ≈ 236k токенов,
   prompt навсегда на хард-пороге, ресет его не понижает.
2. Инверсия порогов: бюджет тримма `num_ctx−1200` был **выше** хард-триггера
   `0.9·num_ctx` — этап 2 физически не мог сработать раньше big-bang.

Фикс (2026-10-10, `tests/test_reminder_dedup_thresholds.py`): дедуп
system-реплик при добавлении (`_append_system_once`); бюджет тримма
`min(num_ctx, HARD_CTX_PCT·num_ctx) − reserve`; ресет выбрасывает старые
протоколы (`OVERFLOW_PROTOCOL_MARKERS`), новый единственный;
`load_messages_snapshot` убирает дубли system-реплик при восстановлении.
Урок: любые «неприкосновенные» сообщения требуют дедупа и контроля размера —
иначе они обходят всю механику вытеснения.

# План доработки (реализован 2026-10-07, см. log.md; коммиты — по решению человека)

Обозначения: **TI** = `core/textual_integration.py`, **SM** = `core/session_manager.py`,
**SMEM** = `tools/session_memory.py`. Этапы 1–3 — ядро (делать в первую очередь),
4–8 — независимые улучшения, порядок внутри произвольный. Каждый этап — отдельный
коммит с тестом.

## Этап 1. `core/session_digest.py` — строитель окон и дайджестов (нулевые риски)

Новый модуль, ничего не меняет в существующем потоке. API:

- `build_windows(session_path) -> list[Window]` — режет `session_raw.log` по
  `metrics`-событиям (каждое = конец вызова модели; начало окна — первый чанк после
  предыдущего metrics), привязывает записи `tools.log` (status=completed) по таймстампам,
  сохраняет для окна: `window_id`, `ts_start/ts_end`, `prompt_eval_count/eval_count`,
  текст финального ответа, список tool-событий (tool, arguments, size), id/номера
  соответствующих сообщений из `context.json` (для указателей).
- `window_cloud(window, prev_clouds) -> str` — ≤10 лемм: токены ≥4 символов из
  (ответ + аргументы инструментов), лемматизация `pymorphy3` (добавить в
  `requirements.txt`; импорт с graceful fallback на суффиксный стеммер, если пакета нет),
  стоп-лист служебных слов, отсев терминов, встречающихся в ≥70% окон.
- `window_line(window) -> str` — формат строки из §7 (goal/done — опциональные поля).
- `merge_old_lines(lines) -> str` — иерархическое сжатие древних строк (частотный
  переизбранный термины + счётчик окон).
- Тест `tests/test_session_digest.py` на фикстурах из `sessions/` (взять 223242 и 230600):
  число окон == числу metrics-событий; облако непустое на содержательных окнах;
  все tool-события привязаны; детерминизм (два прогона — равный вывод).

## Этап 2. Сегментно-границевый тримм в TI

- В `_prepare_messages_for_ollama` (:110) заменить поштучное выбрасывание на выбрасывание
  целыми сегментами: сегмент = maximal'ный блок сообщений от user-сообщения до следующего
  user-сообщения; внутри сегмента пары `assistant.tool_calls ↔ tool` не разрывать.
- Инвариант: на границе вытеснения не остаётся `tool`-сообщения без своего
  `assistant.tool_calls`.
- Прежний артефакт `context_trim_*.json` сохраняется как есть.
- Тест: история с tool-раундами + бюджет, режущий середину — в trimmed нет висячих
  tool-сообщений; system-сообщения целы.

## Этап 3. Блок «забытое» вместо notice (ядро фичи)

- В TI перед каждым запросом (там же, где `_prepare_messages_for_ollama`) собирать/обновлять
  ОДНУ system-реплику `FORGOTTEN_INDEX`: строки окон, вытесненных из контекста (этап 1),
  в бюджете 400–600 токенов; перерасчёт на каждый запрос, реплика заменяется целиком
  (не накапливается).
- Убрать/заменить нынешнюю notice «Контекст был автоматически сокращён…» (:134-141) —
  её роль выполняет блок.
- При overflow-reset (`_ollama_summarize_and_reset_context` :303) блок сохраняется и
  продолжает расти; LLM-протокол остаётся, но строка протокола получает указатель на блок.
- Инструкция модели: короткий абзац в prompts/context_overflow_protocol.txt и tool_policy —
  «это каталог забытого; детали — session_memory get_turn/search по указателям».
- Тест: симуляция длинной сессии → размер блока в бюджете; после reset блок на месте.

## Этап 4. Калибровка оценщика токенов (TI)

- Скользящий коэффициент per-model: после каждого ответа `k = prompt_eval_count /
  _estimate_messages_tokens(prepared)`; хранить EMA (alpha≈0.3) в памяти процесса +
  персист в `performance.log`/метаданные сессии; `_estimate_tokens` умножает на k.
- Начальное k=1.0 (текущее поведение). Эффект: HARD_CTX_PCT начинает означать реальность.
- Тест: синтетическая последовательность метрик → k сходится; деление на ноль защищено.

## Этап 5. Pressure-инжект с гистерезисом (TI)

- Отслеживать долю заполненности (после этапа 4 — калиброванную). При пересечении вверх
  70% и 85% — один раз дописывать в конец `TOOL_RESULT_SUMMARY` (:254) строку уровня
  («контекст 70%, сворачивай рассуждения» / «критично, завершай ход»). Не повторять,
  пока уровень не сброшен (после финального ответа хода или после reset).
- Никаких отдельных сообщений — только строка внутри существующего tool-результата.

## Этап 6. `sign_step` — харнес подписаний

- Новый внутренний инструмент (tools/sign_step.py, регистрация в ToolManager, не
  показывать в чате; результат — «ok»). Схема: `goal` (≤15 слов), `done` (≤15 слов),
  `status` enum [progress|blocked|decision|answered], `entities` (список ≤6).
- Харнес на ходе отслеживает закрытый список observed_entities (пути, URL, имена
  инструментов, аргументы из tools.log этого хода). Валидация: каждая entity — подстрока
  observed (иначе — одна ретрай-попытка с текстом ошибки; затем отказ и механическая строка).
- Форсинг: OpenAI-бэкенд — `tool_choice=required` в финальном раунде хода; Ollama-native —
  директива в tool_policy + существующий паттерн «нет нужного поведения → пинк → нет →
  смириться» (см. MISSING_FINAL_AUTO_CONTINUE). Вызов ожидается ОДИН раз на ход,
  перед финальным ответом.
- Подпись кладётся в дайджест-слой (поле окна), этап 3 подхватывает её в строку блока.
- Тест: валидная/невалидная подпись (левая entity → откат на механическую строку).

## Этап 7. Добивка обрыва по `finish_reason=length` (TI)

- В обработчике стрима: при `length` — сохранить обрубок (включая незакрытый thinking),
  скрытый досыл «продолжи строго с места обрыва», склейка хвоста; шов проверить
  `_detect_repetition` (:155) и убрать дубликат на стыке. Лимит сшивок за ход — 2.
  Пользователю — единый текст.

## Этап 8. Мелочи памяти

- `SMEM._extract_words`: кириллица + леммы (тот же модуль этапа 1) в word_index;
  `.idx` совместить (новые поле `lemmas_index`).
- Новый action `windows` в SMEM: отдаёт `build_windows`/`window_line` — блок и инструмент
  питаются от одного кода.
- Дубли user-реплик в `context.json`: решить на месте — дедуп при записи в
  `SM.update_context` vs оставить партер; предпочесть запись (чистый raw).

## Метрики проверки (после внедрения)

- Число авто-рекавери и overflow-reset'ов за ход (было/стало) — из логов.
- Срабатывания `_detect_repetition`.
- Ошибка оценщика: |prompt_eval_count − est| / prompt_eval_count (этап 4).
- Recall@k блока «забытое»: прогон-аудит на sample-сессиях — отвечает ли указатель строки
  на вопрос «где это было».
- Размер блока в steady-state ≤ бюджета.

## Риски

- `pymorphy3` — новая зависимость (чистый python, офлайн-словарь); fallback обязателен.
- Форсинг tool_choice на нативном Ollama не измерен — этап 6 спроектирован так, чтобы
  провал форсинга стоил нулю (механическая строка).
- Блок «забытое» — новые токены в каждом запросе; бюджет и иерархическое сжатие
  (этап 3) обязаны компенсировать; контролировать метрикой размера.
