# Калибровка «байты → токены» (token_calibrator)

Панель «Производительность» показывает символы/байты, а решения (контекст,
сжатие, скорость) принимаются в токенах. Один коэффициент не работает: плотность
токенов зависит от модели, языка и типа контента. → `concepts/streaming_tui.md`

## Методика (мировой инструмент, не набор констант)
Инструмент не знает ни одной модели заранее — он умеет **учиться на собственном
трафике**:

1. **Контрольный срез** — на каждом завершённом запросе пишется пара
   *(объём текста payload по ролям ↔ точные `prompt_tokens`)* и
   *(символы ответа/размышлений/JSON инструментов ↔ `completion_tokens` /
   `reasoning_tokens`)*. Точные токены сервер отдаёт сам: Ollama — в финальном
   чанке (`eval_count`), OpenAI-совместимый — в SSE при
   `stream_options: {"include_usage": true}` (уже отправляется,
   `core/openai_compat.py`). Это стандартная индустриальная практика
   («measured usage + empirical calibration»).
2. **Ключ метки** — `(отпечаток деплоя, направление, тип вызова)`; отпечаток =
   `модель@сервер` (сменился бэкенд — метки начинаются заново). Направления:
   `prompt`, `completion`, `reasoning`; типы: `plain`, `tool_round`, `summary`.
3. **Каскадный фолбэк** — замер пишется и в точный ключ, и в родительский
   агрегат `(деплой, направление) *`. Оценка идёт сверху вниз: лист при
   `n ≥ MIN_LEAF_N`, иначе родитель при `n ≥ MIN_PARENT_N`, иначе глобальный
   prior. Богатство ключей никогда не оплачивается качеством оценки.
4. **Робастная агрегация** — скользящее окно, МЕДИАНА + MAD (не среднее),
   физический фильтр выбросов (0.02–20 ток/символ).
5. **Детектор дрейфа** — медиана свежих `DRIFT_WINDOW` замеров ушла от
   сохранённой больше чем на `DRIFT_REL` → метка спорная, `ready()` = false
   (панель вправе вернуть байты).
6. **Честность числа** — `estimate()` возвращает статус
   `calibrated | drift | prior`; UI не имеет права показать приближённое как
   точное.

## Фаза 1 (реализована 2026-10-11): тихий сбор
`core/token_calibrator.py` + запись срезов в `core/textual_integration.py`
(после каждого успешного стрима и после нестримингового резюмирования).
Панель **не изменилась** — байты как были. Хранилище — версионируемый JSON
`~/.botinok/token_calib.json` (рядом с базой сессий), атомарная запись,
троттлинг сохранения. Тесты: `tests/test_token_calibrator.py`.

## Фаза 2 (реализована 2026-10-11): панель на токенах
- Все живые строки панели считаются в токенах на каждом тике (10/с):
  «Размышляет» ← направление `reasoning` (фолбэк `completion`), «Написал
  ответ» ← `answer` (completion−reasoning, отдельная плотность — у ответа и
  размышлений она разная), «Готовит команду» ← `completion`, «Скорость» ←
  Б/с × плотность `completion`. Байты остаются бледной подписью в скобках
  (индикатор движения; детектор зависаний по-прежнему завязан на байты).
- Токены показываются с первого же среза: до накопления — по prior (всё равно
  с «~»), после — по медиане замера.
- **Серый прогноз контекста**: во время живого стрима (чанк < 2 с назад)
  «Диалог занял» и полоса `#ctx_bar` дорисовывают серый хвост `+~N ток`
  (зарождающиеся токены хода, класс `ghost`); с приходом фактического usage
  (done-чанк) прогноз исчезает, цвет (low/mid/high) возвращается.
- Потребители токенов переведены на калибратор: `_estimate_message_tokens`
  (бюджет тримма, HARD_CTX, карта контекста, «Память сжималась», «Диалог
  занял», forgotten-block) использует плотность `prompt` при `calibrated`;
  EMA `len//4` остался запасным путём (resume, холодные модели).
- «АПИ отдано/принято» остаётся байтами — это транспорт (SSE-конверт раздувает
  его в десятки раз, токены по байтам транспорта не считают).

## Эмпирика (полигон на старой базе, окт. 2026)
302 хода из 103 сессий: вывод ≈ 0.33 ток/символ (медиана; ru/en/код лежат в
0.31–0.39 — языковые страты на первом этапе не требуются), модели различаются
на ~10% (0.333–0.350) — метка «на модель» оправдана. Текущая эвристика
`len//4` (`calibrate_token_estimator`, EMA) недооценивает вывод вдвое; после
одной метки MAPE канала вывода ≈ 18%. Промпт-канал по истории не восстанавливается
(снапшот ≠ запрос из-за tool-раундов) — поэтому и нужен per-request сбор.
