# Стриминг и производительность в TUI

Проект сильно оптимизирован под низкую VRAM и слабые терминалы. Визуализация — Textual UI (старый `BotVisualizer` на Rich удалён в 0.4). → `entities/textual_ui.md`

## Ключевые улучшения (из git-истории)
- Замена Rich Live на **Textual TUI** для плавности (FPS 10/30); Rich-движок полностью удалён. → `comparisons/rich_vs_textual.md`
- **Единая точка вывода** `stream_static`: весь поток рендерится там; «спойлеры» открываются/закрываются по очереди → **нет мигания** в терминале.
- Живое markdown-форматирование стрима ассистента.
- Исправления мерцания в SSH-терминалах с низкой скоростью (Rich-эпоха).
- Компактный прогрессбар контекста.

## Остановка по Esc (обрыв генерации модели)
`response.close()` **не** прерывает блокирующий read в потоке-читателе
(`_stream_reader` → `response.iter_lines()`), поэтому UI вставал, а модель
продолжала генерировать. `_abort_stream(response)` делает `shutdown(SHUT_RDWR)`
сокета (через `response.raw._fp.fp.raw._sock`, для OpenAI-обёртки — `._resp`),
разблокирует read и рвёт соединение — сервер (Ollama) прекращает генерацию.
Ход завершается: частичный ответ сохраняется, `stopped_by_user` →
`_finalize_turn`, дальше не идём. Запущенный инструмент **мягко** останавливается
своим `run()` по флагу (`process_control.signal_stop()`); `kill_all` из
обработчика клавиши не зовётся, чтобы не рвать запись сессии. После остановки
агент ждёт следующее сообщение — без авто-продолжений.
→ `entities/process_control.md`

**Почему Esc «не прерывал» (доказано 2026-09-19).** Проверка `_stop_requested`
стояла только между пачками дренажа, а `append_assistant_chunk` на каждом чанке
пересобирал весь накопленный текст (O(n²)) — UI насыщался, воркер висел в
`call_from_thread` и не доходил до проверки. Исправлено: троттлинг отрисовки
(≈10/с, текст копится полностью), независимый сторож в `_stream_turn` (по флагу
сразу `_abort_stream`) и проверка флага на каждом чанке. Esc из встроенного
терминала при идущем ходе не уходит в PTY; «ход идёт» = стрим **или** инструмент
(`turn_in_progress`). Тест `tests/test_escape_stream.py` (mock-модель, оба пути)
без фикса падает, с фиксом проходит.

**Зависший сервер.** Запрос стрима выполняется в отдельном потоке
(`_post_stream_interruptible`), поэтому Esc возвращает управление даже если
сервер не отдал заголовки. В панели ожидание сервера показывается отдельной
строкой «Ждём сервер: N — попытка K», а не «модель молчит / зависло».

## Устойчивость к сбоям API (сессия «держится зубами»)
При временных сбоях сервера модели (сеть, `429/500/502/503/504`) агент не
завершает ход: `_try_hold` ждёт сервер с растущей паузой, пока не восстановится.
- Бюджет ожидания — `RetryBudgetSec` (по умолчанию сутки), пауза — экспоненциально
  до `MaxRetryBackoffSec` (60 с). Прерывание — `Esc`.
- **Ошибка печатается один раз**, рядом растёт счётчик: в панели строка
  «Ждём сервер: N с (попыток: K)». Спама однотипных строк нет.
- Счётчики сбрасываются при успешном стриме; ход при этом не теряется —
  повторяется тот же запрос (бэкенд stateless).
- Постоянные клиентские ошибки (`400/401/403/404`) не пережидаются: они
  сохраняются как прерванный ход с пометкой (кроме спец-случая «нет tools»).
- **Не путать с защитой от «тихой смерти» модели**: пустое завершение
  (`_is_empty_completion`) повторяется до `MAX_EMPTY_RETRIES_PER_TURN`, а текст
  «Сессия не завершена — продолжай с того же места» сохраняется в контекст.
  → `concepts/session_resume.md`

## Устойчивость к пустым/оборванным ответам
Модель может вернуть **полностью пустое завершение** (нет `content`, `thinking` и
`tool_calls`), хотя бэкенд насчитал токены (`eval_count > 0`). Раньше это молча
сохранялось как финальный ответ и гасило ход — снаружи «ответ оборвался молча».
Теперь `_is_empty_completion()` распознаёт такой сбой: harness пишет видимую
пометку и системную заметку в сессию, повторяет запрос (промпт
`auto_continue_final`) до `MAX_EMPTY_RETRIES_PER_TURN`, а при исчерпании —
останавливается с явным сообщением и ждёт следующее сообщение. Обрыв по
повторам (`_detect_repetition` → `_abort_stream`) тоже логируется, а не проходит
молча. Рядом живут авто-восстановление при пустом тексте с непустым reasoning,
детекте повторов и переполнении контекста. → `entities/process_control.md`

## Панель «Производительность» (простая и живая)
Требование: пока задача не завершена, в панели **всегда есть движение**; если
что-то зависло — нарастающие счётчики проблем. Всё на простом русском. → `entities/textual_ui.md`

- **Живое ядро**: «Что сейчас» (русская фраза + спиннер), «Всего прошло», «Этап»,
  «Первый ответ», «Размышляет»/«Написал ответ» (размер уже пришедшего текста,
  растёт во время генерации), «Скорость» (Б/с), «Модель молчит».
  `_tick_stats` форсирует перерисовку 10 раз в секунду, пока задача активна
  (`_task_active`).
- **Раньше было заморожено**: счётчики Thinking/Response/Tool/TTFT/TPS
  записывались только по завершении потока (`_update_stats` в блоке `done`),
  поэтому во время генерации показывались значения прошлого захода. В Rich Live
  они считались на лету. Историю см. `comparisons/rich_vs_textual.md`.
- **Профили сервера** (`stats_data["server"]`): Ollama (расширенный) показывает
  «Видеопамять» и «Готовит команду»; OpenAI-совместимый эти строки скрывает —
  сервер их не сообщает. «АПИ отдано/принято» есть в обоих.
- **Трафик модели**: «АПИ отдано» / «АПИ принято» за запрос и за сессию +
  скорость приёма. → `entities/net_meter.md`
- **Детектор зависаний** (пороги): молчание модели — жёлтый с 10 с, красный с 30 с;
  работающий инструмент — жёлтый с 1 мин, красный с 5 мин. При превышении —
  растущий счётчик и подсказка «нажмите Esc».
- **Ожидание сервера отдельно**: при сетевых повторах (`retries`/`retry_wait`)
  строка «Ждём сервер: N — попытка K», а не «модель молчит / зависло».

## Стоимость отрисовки (CPU)
Метрики обязаны обновляться быстро (10/с), но перерисовка не должна тянуть весь
экран. Замеры (headless, длинная сессия):
- **простой**: раньше ~25% одного ядра (форсированный dirty 10/с гонял полную
  пересборку Textual) → теперь ~4%; метрики в покое не перерисовываются;
- **активный ход**: ~10% одного ядра, метрики по-прежнему 10/с.
- Ключевое: `Static.update(..., layout=False)` для метрик и шапки (layout —
  только когда меняется число строк), поэтому обновление метрик **не вызывает
  `chat.refresh`** (проверено: 0 за 2 с). Раньше `refresh(layout=True)` каждый
  тик инвалидировал layout всего дерева — это и «перерисовывало весь чат».

## Цвета контекста
Полоса заполнения памяти диалога (`#ctx_bar`) и строки контекста: зелёный
(<70%), жёлтый (70–90%), красный (≥90%).
