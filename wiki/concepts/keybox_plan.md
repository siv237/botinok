# Ключница — план реализации

Универсальный примитив харнеса: **«запросить учётку у человека»». Секреты (логин/пароль/ключ) живут вне контекста модели: модель оперирует именами, значение подставляется на границе процесса. Назначение — доступ к корпоративным ресурсам (порталы, ssh, sudo, Kerberos, RDP, IMAP) без «напиши мне пароль в чат».

## Принцип

- Модель **никогда не видит значений** — только имена целей (`portal.corp`) и факт «учётка выдана».
- Решение о хранении принимает **человек** в момент ввода (чекбокс), а не архитектура.
- Лестница трения — настройка пользователя: каждый раз вводить пароль → раз в TTL мастер-пароль → никогда (кэш).

## v1 — диалог + RAM (без хранения)

1. Примитив `sm.credentials.get(target)` (`core/keybox.py`): блокирует ход, поднимает диалог «Ресурс: X — логин / пароль» (скрытый ввод), значение кэшируется в RAM сессии по цели.
   - TUI: инлайн-виджет dangerous mode + `Input(password=True)`.
   - Одиночный режим: `getpass` в tty (тот же механизм, что dangerous-спрос по ходу).
   - Pipe/stealth: отказ с инструкцией («спросить некого»).
2. `web action=login url=...`: web-кит парсит форму (CSRF), берёт учётку из брокера, POST'ит, получает куки.
3. **Cookie jar**: `requests.Session` per-host, переживание в директорию сессии (JSON). Пароль запрашивается один раз на протухание сессии портала, дальше летают куки.
4. **Привязка к хосту**: учётка хранится под именем цели и за её пределы резолвером не выносится.
5. **Маскирование**: резолвер знает значения → в `tools.log`/`session_raw.log` значения пишутся `***`; в сессии остаётся запись «✓ учётка `user_1` выдана для portal.corp».

## v2 — хранение (opt-in)

- В диалоге чекбокс «сохранить». Файл `~/.botinok/keys.enc` = **AES-GCM(cryptography), ключ — scrypt(мастер-пароль)** (библиотека `cryptography` — пинится в requirements.txt; в venv присутствует как сирота, узакониваем).
- Мастер-пароль спрашивает OUR диалог (единый UI), кэш разблокировки в RAM с настраиваемым TTL.
- Неверный пароль портала — не сохранять, переспросить.
- Будущие бэкенды хранения (симметричный возраст не поддерживает мультиреципиентов): age на SSH-ключ / gpg — интерфейс `keybox.py` не меняется. Сценарий поддержки («зайди под моей доменной учёткой» с чужой UNIX-учётки): `grant`/recipients — отложено до реального спроса.

## Универсальные потребители

| Потребитель | Канал доставки значения |
|---|---|
| web-формы | прямой вызов в web-ките |
| ssh | `SSH_ASKPASS=<ботинок-askpass> SSH_ASKPASS_REQUIRE=force`, хелпер → unix-socket → диалог |
| sudo | `SUDO_ASKPASS` + `sudo -A`, тот же хелпер |
| kinit (Kerberos) | stdin |
| RDP/прочее | temp-файл 600 / stdin; argv — крайний случай (видно в ps) |
| python-скиллы | `sm.credentials.get()` in-process |

Хелпер — скрипт ~30 строк на stdlib-сокетах; значения не появляются в argv/env/ps.

## Пайплайн (эталонный кейс portal.corp)

Запрос → `web action=open` (форма распознана) → `web action=login` → резолвер: кэш/хранилище/диалог → проверка привязки к хосту → POST (значение в TLS-теле) → 302 + кука в jar → модели только результат («вошёл как Иванов, admins»). Ошибочный пароль → переспрос, не сохранять.

## Модель угроз (честно)

- Шифрование v2 — **гигиена** (секрет не уедет в историю сессий/git/шаринг/другого UNIX-пользователя), а не броня от того, кто работает под твоей учёткой.
- Промт-инъекция не может процитировать невидимое; не может и вывезти без привязки к хосту; отправка секрета на незнакомый хост = dangerous-подтверждение **с адресатом на экране**.
- Поддержка на машине юзера: каждый ботинок работает под своей UNIX-учёткой со своей ключницей; наблюдаемость — общая папка сессий + «кто запущен» в шапке (мелкая доработка харнеса).
